## 一、总体架构

```
                       ┌──────────────────────────────────────────┐
   用户截图文件夹 ─────►│  模块1 index  扫描 + hash/mtime 变更检测   │
   （png/jpg/jpeg/      │               ▼                          │
     bmp/webp，递归）    │        SQLite 索引库（不入 git）           │
                       │        files / ocr_text / chunk / fts     │
                       └──────────────┬───────────────────────────┘
                                      │
                       ┌──────────────▼───────────────────────────┐
                       │  模块2 ocr   RapidOCR onnx CPU 批量识别   │
                       │              失败标记 + 可续跑            │
                       └──────────────┬───────────────────────────┘
                                      │
   查询词 ─────────────►┌──────────────▼───────────────────────────┐
                       │  模块3 search  FTS5 双分词路径 + 稳定排序 │──► 命中图片列表
                       └──────────────────────────────────────────┘   （路径 + 缩略图）

                       ┌──────────────────────────────────────────┐
                       │  模块4 dedupe  pHash 分组 → 建议清单 CSV  │──► 建议清单（只读）
                       └──────────────────────────────────────────┘

                       ┌──────────────────────────────────────────┐
                       │  模块5 bench  合成图生成器 + manifest 真值 │──► 对账报告
                       └──────────────────────────────────────────┘
```

**分层纪律**：`cli` 只做参数解析与编排；`config` 承载全部数值口径（唯一来源）；`index/ocr/search/dedupe` 是纯业务层，互不 import 对方的私有实现，只经 `db` 读写索引库；`bench` 只消费公开 API 与 manifest，不反向依赖 CLI。

## 二、技术选型表

| 层 | 选型 | 理由 | 被否方案 |
|---|---|---|---|
| 语言/运行时 | Python 3.8+（本机实测 3.8.8 与 3.12.10 双通道） | 底线 3.8 保兼容；跨版本行为差异由 CI 矩阵兜 | 3.10+ 独有语法（`write_text(newline=)` 等）禁用 |
| 索引库 | SQLite（stdlib `sqlite3`） | 零额外依赖、单文件、可 `FTS5` | 自建倒排索引（重复造轮子）、外部 ES（违背纯本地轻量） |
| 全文检索 | FTS5 + **双分词路径**（见 §三） | 中文检索是核心能力；双路径保"永远可用" | 纯 `LIKE` 扫描（无排序语义、大库慢） |
| OCR 引擎 | `rapidocr-onnxruntime==1.4.4`（onnx CPU） | pip 可装、CPU 可跑、无 GPU 依赖、**wheel 自带模型** | 自研 OCR（题目文档已弃）、PaddleOCR（依赖重） |
| 相似图 | pHash（`imagehash`） | 题目文档指定；位级可复现 | 感知哈希自研（可作兜底，见决策记录 D-5） |
| 合成图渲染 | Pillow（PIL） | 程序化渲染已知文本 + 真值植入 | 手工截图（不可复现、含真实信息风险） |
| CLI | `argparse`（stdlib） | 零依赖、退出码可控、`--help` 可被守门反射 | click/typer（多一层依赖，收益低） |
| 打包分发 | 源码包 + `pip install -e .`（首期不做 exe） | 首期交付形态为 CLI 源码；exe 留扩展 | PyInstaller（首期无必要，且引入构建漂移面） |
| 测试 | pytest（dev extra） | 本机 3.8/3.12 均已具备 | unittest（生态弱） |
| CI | GitHub Actions，矩阵 windows-3.8 / windows-3.12 / ubuntu-3.12 | 跨版本 + 跨平台双覆盖 | 单平台（跨环境盲区，见 skill 验收门） |

## 三、中文分词双路径设计（本项目的核心工程决策）

### 3.1 阶段 0 预检实测（证据先于设计）

| 实测项 | 命令要点 | 实测结论 |
|---|---|---|
| FTS5 可用性 | `CREATE VIRTUAL TABLE t USING fts5(a)` | 3.8.8 / 3.12.10 双通道均 **OK**（sqlite 3.34.0 / 3.49.1） |
| 内置 tokenizer | `tokenize=trigram/porter/unicode61` | 双通道均 OK |
| `trigram` 对短中文查询 | 索引"本月账单已生成"，查 `账单` | **0 命中**（trigram 需 ≥3 字符；2 字查询失效）→ **不可作兜底路径** |
| 逐字切分 + `unicode61` | 索引前把 CJK 逐字空格分隔，查询同样切分并作 phrase 匹配 | 查 `账单` → **2 命中**；`本月账单` → 1；英文 `error occurred` → 1 → **可作兜底路径** |
| `libsimple` pip 轮子 | `pip index versions simple-tokenizer` | 仅 `cp314-manylinux_2_34_x86_64` 轮子（3.8/3.12 + Windows **不可用**） |
| `libsimple` 预编译件 | GitHub Release v0.7.1 assets | 提供 `libsimple-windows-x64.zip` / `linux-ubuntu-latest.zip` / `osx-arm64.zip` 等（**可下载**） |
| **`libsimple` 实际加载与分词** | **M1 实测**（`plan/verify` §M1 一） | ✅ **双通道均加载成功**；`tokenize='simple'` 已注册；词级切分只能经 `jieba_query()`；⚠️ 词典缺失时 **FATAL 中止进程（exit 127）** → 接线须**前置词典校验** |
| sqlite 扩展加载能力 | `conn.enable_load_extension(True)` | 双通道均 **OK**（具备加载 `simple.dll` 的能力） |

### 3.2 双路径落法（两条路径均须可用）

**统一抽象**：分词不是"交给 sqlite 的 tokenizer 参数"，而是**索引期与查询期共用的一个纯 Python 函数** `segment(text, profile) -> str`（CJK 按 profile 切分、ASCII 词保持整体，用空格连接）；FTS5 表固定用 `tokenize='unicode61'`，只吃这个函数的输出。

| 路径 | profile | 切分规则 | 可用条件 | 定位 |
|---|---|---|---|---|
| 主路径 | `simple` | CJK 用 libsimple **词级**切分（`simple.dll` 加载 + `jieba_query()` 提取词） | 用户提供 DLL **且词典 5 件齐备**（M1 实测） | 词级精度更好，但**召回更低**（实测 0.8438 < char 0.9375） |
| 兜底路径 | `char` | CJK **逐字**切分（unigram），查询词作 phrase 匹配 | **无条件可用**（纯 Python） | 保证"永远能查"；**默认 profile** |

三条纪律：
1. **索引库记录所用 profile**（`meta.tokenizer_profile`）；查询时 profile 不匹配 → 显式报错（exit 2）并提示重建，**绝不静默按错口径检索**。
2. **主路径不可用不冒充可用**：`simple` profile 加载失败时显式报告"未启用 + 原因"，检索仍走 `char` 兜底（与 skill"未启用不冒充通过"同源）。
3. **两条路径都要有真调用它的测试**（不是只测定义）：`char` 路径的短中文查询回归测试锁死；`simple` 路径用桩/真 DLL 二选一，DLL 缺席时走 `not_enabled` 显式声明（零调用点 = 空转）。

**查询语义（写进 README，避免用户预期落差）**：中文为**子串语义**（逐字 phrase 匹配，"账单"命中"本月账单已生成"）；英文为**词/前缀语义**（`config*` 前缀可命中 `configure`），英文词内子串（`ccount`）不命中——这是"按图中文字检索"场景的合理取舍。

## 五、数据模型（SQLite 索引库 schema v1）

```sql
-- 元信息：库版本、分词 profile、阈值快照（口径可核）
CREATE TABLE meta (key TEXT PRIMARY KEY, value TEXT NOT NULL);

-- 模块1：文件台账（一文件一行，path 唯一）
CREATE TABLE files (
  id        INTEGER PRIMARY KEY,
  path      TEXT    NOT NULL UNIQUE,   -- 绝对路径（归一后）
  size      INTEGER NOT NULL,
  mtime_ns  INTEGER NOT NULL,          -- 纳秒级，避免秒级同值漏检
  width     INTEGER, height INTEGER,   -- 图像尺寸（读失败为 NULL）
  file_hash TEXT,                      -- 内容 sha256（读失败为 NULL）
  status    TEXT    NOT NULL,          -- pending|indexed|ocr_failed|missing
  ocr_tries INTEGER NOT NULL DEFAULT 0,
  ocr_error TEXT,                      -- 末次失败原因（可续跑定位）
  first_seen_ns INTEGER NOT NULL, last_seen_ns INTEGER NOT NULL
);

-- 模块2：OCR 结果（一文件一行；文本全文 + 平均置信度 + 模型版本）
CREATE TABLE ocr_text (
  file_id   INTEGER PRIMARY KEY REFERENCES files(id),
  text      TEXT    NOT NULL,          -- 行文本按 \n 连接（顺序 = 引擎输出顺序）
  line_json TEXT    NOT NULL,          -- 逐行 box/text/conf（确定性 JSON，供口径核验）
  mean_conf REAL    NOT NULL,
  line_count INTEGER NOT NULL,
  engine    TEXT    NOT NULL,          -- 引擎+版本（可追溯）
  run_sig   TEXT    NOT NULL           -- 输入签名（file_hash+profile+阈值），防陈旧覆盖
);

-- 模块3：检索（chunk = 一行文本，便于高亮与稳定排序）
CREATE TABLE chunk (
  id INTEGER PRIMARY KEY, file_id INTEGER NOT NULL REFERENCES files(id),
  line_no INTEGER NOT NULL, text TEXT NOT NULL
);
CREATE VIRTUAL TABLE chunk_fts USING fts5(
  text, content='chunk', content_rowid='id', tokenize='unicode61'
);  -- text 列为 segment() 后的空格连接串
```

**写入纪律**：全部写盘经 `db.write_txn()` 单点（原子事务）；索引库文件路径由用户指定（默认 `<目标文件夹>/.picrecall.db`，可 `--db` 覆盖）；**`.picrecall.db` 与 `*.db` 均在 `.gitignore` 内**。

## 六、确定性设计（"重跑一致"是承诺，不是期望）

| 面 | 落法 |
|---|---|
| 扫描顺序 | 路径归一后 `sorted()`；不用 `os.scandir` 返回顺序、不用 `set` 迭代序 |
| 变更检测 | `file_hash`（sha256 内容）+ `mtime_ns` 双重比对；hash 相同即视为未变更 |
| OCR 结果绑定输入身份 | `run_sig` = sha256(file_hash + 引擎版本 + 阈值 + profile)。内容变更 → **作废派生行**（防陈旧文本被检索）；磁盘与台账 `file_hash` 不符 → **拒绝落库**并提示重建（K4，M3 定案；见 plan/04 §四） |
| 检索排序 | `ORDER BY rank, files.path`（rank 并列时以路径为决定性 tie-breaker） |
| 合成图/清单落盘 | 无时间戳、无随机序（固定 seed 的自研确定性 RNG）、LF 行尾、UTF-8 无 BOM |
| 序列化 | 统一 `serialize.py` 单点：`json.dumps(sort_keys=True, ensure_ascii=False, indent=2)` + LF + 结尾换行 |

## 八、风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| libsimple DLL 在用户机器上加载失败 | 主路径不可用 | `char` 兜底无条件可用；显式报告"主路径未启用"；README 给 DLL 获取与放置说明 |
| 3.8 通道 onnxruntime 版本上限（1.19.2） | 新版特性不可用 | pyproject 按解释器分档约束：`onnxruntime<1.20; python_version<"3.9"` |
| OCR 在低配机器慢 | 建索引体验差 | 批量+可续跑+进度输出；README 明示"首建索引耗时与图片数成正比" |
| 截图含敏感信息 | 隐私风险 | 零出网、索引库不入 git、合成数据用假值白名单（data/README §三） |
| pHash 阈值过松/过紧 | 建议清单可用性 | 阈值一处定义；基准含"应分到一组/不应分到一组"双向样例 |
