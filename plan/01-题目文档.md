# 10-16-2-pic-recall · 截图文字检索库（题目文档 v1）

> **性质**：不参赛项目题（发布 GitHub 公开仓库，署名 yuluo554）
> **目标产出**：仓库 `10-16-2-pic-recall`，形态 = 纯本地 Python CLI + 可选本地 HTML 界面
> **版本史**：v1 · 2026-10-15 · 初版定稿
> **定位宣言**："我记得截过一张图，上面写着XXX，但找不到是哪张"——对本地截图文件夹做一次性 OCR 索引，之后按图里的文字秒级搜回那张图（含增量索引、重复截图合并）。OCR 引擎已是成熟基建，但"索引 + 检索 + 增量 + 去重"这一层没人做。

## 一、介绍

截图囤积是普遍习惯：聊天记录、报错弹窗、账单页面、配置说明，随手一截就进文件夹，数量动辄数千。等需要回找时，只能按文件名或翻图，找不到。

- 现有 OCR 引擎（RapidOCR、Umi-OCR 等）解决的是"识别这一张图"，是**识别工具**，不做持久化索引与增量检索；
- 剪贴板类工具（One-Clip 等）解决的是"剪贴板历史"，不是"按图中文字检索已囤积的截图文件夹"；
- GitHub 检索 `local screenshot text search ocr` 相关项目近乎空白（基准日 2026-10-15，检索式见 data/README，软论据）。

本项目 = 在成熟 OCR 引擎之上做**索引 + 检索 + 增量 + 去重**这一层：一个纯本地、零上传、可增量维护的"截图文字检索库"。

## 二、任务要求（首期 5 个模块，其余留扩展）

### 模块 1：图片导入与增量索引
- **输入**：用户指定的本地截图文件夹（递归扫描 png/jpg/jpeg/bmp/webp）。
- **输出**：SQLite 索引库（不入 git），记录 文件路径 / 文件 hash / mtime / 尺寸 / 索引状态。
- **纪律**：变更检测以 `文件 hash + mtime` 双重比对；**索引内容与文件 hash 绑定，重跑一致**；删除文件只标记失效，不动用户文件。

### 模块 2：OCR 识别管线
- **输入**：索引库中待识别的图片（新增/变更）。
- **输出**：识别文本 + 置信度写入索引库。
- **引擎**：RapidOCR（onnx，CPU 推理，无 GPU；模型首次运行下载，约 100-200MB）。
- **纪律**：批量识别 + 失败重试（失败项标记状态、可续跑）；OCR 置信度阈值在代码中一处定义；**同一张图重跑 OCR 结果一致方可覆盖入库**。

### 模块 3：FTS5 全文检索
- **输入**：中文/英文查询词。
- **输出**：命中的图片列表，按时间/相似度排序，附预览缩略图（CLI 输出路径 + 可选 HTML 预览）。
- **引擎**：SQLite FTS5；中文分词用 wangfenjin/simple tokenizer，不可用时按字 ngram 兜底（两条路径均须可用）。
- **纪律**：同一查询词对同一索引库重复执行结果一致（排序稳定）。

### 模块 4：重复截图合并
- **输入**：索引库中图片的 pHash（imagehash 库）。
- **输出**：pHash 相似分组 + **保留建议清单**（CSV/文本），不直接删除任何文件。
- **纪律**：pHash 相似阈值一处定义；**默认只读，绝不自动删除**。

### 模块 5：真值基准
- **输入**：无（程序化生成）。
- **输出**：合成截图集——用 PIL 渲染带已知文字的图片（白名单文本集，见 data/README），并**植入真值**：每张图对应的应命中查询词与图片对应关系；附 OCR 识别率口径声明（以合成图上"应识别出的文本行是否被检出"计）。
- **纪律**：真值以 manifest 文件随数据入库；基准可一键重跑，结果与 manifest 对账。

### 扩展项（不进首期承诺）
- 本地 HTML 界面（检索/预览/重复合并可视化）；
- 更多语言 OCR；
- 按相似图搜图（以图搜图）。

## 六、边界与非目标

- **不做** AI 图片理解 / 语义搜索：只做 OCR 文字检索，语义检索留扩展项；
- **不做** 云同步、不上传任何内容；
- **隐私红线**：截图常含敏感信息（聊天记录/账单），**纯本地、零上传、零遥测；索引库不入 git**；
- **默认只读**：不删不改用户文件；重复合并只输出建议清单；
- **品牌隔离**：本仓库文档不提及任何姊妹项目；
- **首期范围限定**：上述 5 个模块，其余一律标扩展项，防 scope 失控。
